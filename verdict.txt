## Review of the roadmap

### What is right about it

- Owning the telemetry source is the correct call. Building the app that emits the events means you can answer "how do you know this field is trustworthy?" for every event. That question kills most portfolio detection projects built on downloaded Sysmon samples.
- Server-side derivation of actor, outcome, and IP; a separate trusted ingestion path; event-ID uniqueness; deterministic alert identity; replay producing no duplicates. These are exactly the things production pipelines get wrong, and they are cheap to test.
- Audit event and business change in one transaction, with denials still logged. Most junior candidates have never thought about what happens when logging fails.
- Distinct-resource thresholds in R2/R4 instead of raw counts. Rolling windows in Python vs. fixed buckets in SPL as an explicit comparison. Both are real analyst conversations.
- The per-rule documentation template (hypothesis, blind spots, benign causes, suppression, tests) is how detection engineering teams actually write rules.
- The honesty constraints ("threshold-based, not ML", "presigned URL does not prove download", "no tamper-proof logging") are the most interviewable trait of the whole document.

### Gaps I would fix before the first session

1. Threat model is scheduled too late. It is in weeks 5-6, but it decides which events you emit on day 7. Write a half-page version on day 1 (assets, actors, what abuse looks like) and expand it later. Hypothesis before telemetry is the correct order; the roadmap even cites the book that says so.
2. Event types are missing the most interesting denial. `document_access_denied` covers documents, but a member hitting `/security/alerts` is the highest-value denial in the app and there is no event for it. Use a generic `access_denied` with `resource_type` (document, alert, admin_route) rather than a document-specific type.
3. `role_changed` needs `previous_role` and `new_role` as real fields, not buried in `metadata`. R3 depends on knowing which transitions count as increases; that logic needs typed inputs.
4. Add `session_id` to the contract (an opaque ID, never the cookie value). It lets you attribute downloads to a specific authentication rather than just to an actor, which is what R3 and R4 actually want, and it is how real investigations pivot.
5. Define what `document_downloaded` means when documents are text in Postgres. Either every `GET /documents/{id}` is an access, or there is a distinct `/download` route. R4 is ambiguous until you pick.
6. Account lockout is unaddressed. Any real app locks after N failures, which would suppress R1 entirely. Decide explicitly: no lockout in v0.1 (so R1 has signal, documented as a deliberate control gap), or lockout at a threshold above R1's. Either way, the interplay between a preventive control and a detection is a strong interview story; do not leave it implicit.
7. R1's real blind spot is password spraying: many accounts, one or two failures each, one source. Grouping by account misses it by design. The "practice" variant on day 4 should be distinct accounts per source IP (spray), not distinct IPs per account. Document spray as R1's blind spot from the start.
8. Add a `detection_runs` table (run_id, started_at, lookback window, events_scanned, alerts_created, alerts_suppressed). It costs an hour and answers "how do you know the detector ran, and over what?" It also gives you the honest lab metrics the roadmap wants without inventing anything.
9. Expected results for fixtures must be hand-written before the detector runs, or the tests are tautological. The roadmap hints at this; make it a hard rule.
10. Source IP in Docker Compose will be the bridge gateway for every request. All IP diversity will come from fixtures. Fine, but say so, and do not build IP-based logic that you can only exercise with fixtures.

### Scope and time

- 30-45 hours for v0.1 is still optimistic if you are at the week-1 Python stage. Days 7-9 (auth, two tenants, RBAC, CRUD, event emission, R2) and days 10-11 (a React app with login, docs, and analyst views) are each closer to 15 hours for someone learning the stack.
- If hours run short, cut the React UI first, not the detections. Junior analyst interviewers care about the pipeline, the rules, and your ability to explain evidence. A `curl` walkthrough of `/security/alerts/{id}` is an acceptable v0.1 analyst interface; the UI can be the first v1.0 item.
- MITRE mapping: only R1 (T1110.001, password guessing) and R3 (T1098 account manipulation, T1078 valid accounts) have defensible mappings. R2 and R4 should say "no mapping" rather than stretch.
- Splunk licensing genuinely needs checking before you commit hours; the roadmap already flags this. Keep the "one SIEM query language" skill regardless of vendor outcome.

### Verdict

The scope cut is correct and the design constraints are more mature than most junior candidates' actual work. The gaps above are all data-contract and sequencing fixes, not architectural ones. Fix items 1-6 in the technical doc before writing code and the roadmap is sound.
