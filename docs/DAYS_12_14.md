
## Regression tests versus CI

A regression is a behavior that worked, then broke because of an unrelated change. The
benign tests pin the two behaviors that make R1 and R2 meaningful:

```text
4 failures, then success          -> 0 R1 alerts   (the threshold is 5, not "some")
5 denials of doc-alpha-001        -> 0 R2 alerts   (R2 counts distinct documents, not requests)
```

The pure detectors already had these cases as unit tests. The new tests drive the same
situations through the login route, the documents route, the audit writer, PostgreSQL,
and the runner. If a later change made R2 count raw requests, or made the login route
record one event twice, they would fail.

Tests answer "does it behave correctly?" CI answers "is that checked on every change,
whether or not I remember to run it?" CI adds no new checks; it runs the existing ones on
every push and pull request. One detail matters: the database suites skip rather than
fail when PostgreSQL is unreachable, which is convenient locally but would let CI pass
without testing anything. The workflow therefore fails if pytest reports any skip.

Frontend tests prove the UI handles `401`, `403`, and `404` correctly. They do not prove
authorization, because anyone can call the API without React. That proof stays in the
Python tests against real PostgreSQL.

## Migrations versus seed data

```text
empty PostgreSQL --migrate--> correct schema --seed--> known fictional state --scenario--> telemetry
```

- **Migrations** (`backend/migrations/*.sql`, `scripts.migrate`) define structure:
  tables, constraints, indexes. They are applied once each and recorded in
  `schema_migrations`.
- **Seed** (`scripts.seed`) inserts the fictional organizations, users, and documents
  every scenario assumes. It is idempotent.
- **Telemetry** is what activity produces: sessions, events, alerts, and detector runs.
  `scripts.reset_telemetry` removes only this layer, so the same scenario replayed from
  the same seeded state produces the same alerts.

Same starting state plus same actions gives the same result. That is what makes the
demo and the acceptance run below repeatable. It extends the determinism the detectors
have had since Days 1–4, where events are sorted by time and event ID.

## Event, detection, alert, investigation

```text
Event          something happened                  Alice failed a login
Detection      a pattern matched                   five failures, then success
Alert          this deserves analyst attention     R1 fired, severity medium
Investigation  evidence and context interpreted    timing, IPs, account, later activity
Conclusion     suspicious / benign / unresolved    "suspicious, not proven compromise"
```

R1 and R2 stop at "alert". The [investigation](investigations/R1_alice_failed_logins.md)
shows the next steps: counting the evidence against the threshold, noticing that six
attempts in 203 ms cannot be a person typing, listing competing explanations, and naming
the data that would settle it.

## Release acceptance

Run on 2026-09-26 on macOS with Docker, Python 3.14, and Node 26. The repository was
copied to an empty directory with a new virtual environment, a new `.env` built from
`.env.example`, and its own Compose project, port, and volume. The README was followed
as written.

| Check | Result |
| --- | --- |
| `pip install -e '.[dev]'`, Compose, both migrations, seed | Succeeded without manual database work |
| `python -m pytest -rs` | 134 passed, 0 skipped |
| `npm ci`, `npm test`, `npm run typecheck`, `npm run build` | 0 vulnerabilities; 7 passed; clean; built |
| `reset_telemetry` without `--yes` | Named the target database, deleted nothing, exit 2 |
| Suspicious scenario: statuses | Bob 200 own document; 403 ×4; 404 ×1. Alice 401 ×5, then 200 |
| Suspicious: detector run 1 | 12 events; R1 created 1; R2 created 1 |
| Suspicious: detector run 2 | R1 and R2 created 0, unchanged 1 |
| Suspicious: alerts via the UI proxy | 2. R1 5/5 with 5 `failed_login` + 1 `successful_login`; R2 5/5 on `doc-alpha-001`, `-002`, `-003`, `-005`, `doc-beta-001` |
| Wrong role, direct API | Bob `/security/alerts` 403; analyst `/documents` 403 |

| CI skip guard with unreachable database | 70 skipped, and the guard failed the job |

The UI proxy check fetched the analyst session, alert list, and alert details through
Vite's `/api` proxy. Page rendering is covered by the frontend tests and the recorded
demo.

## Limitations of this phase

- CI is defined but proven only once it runs on GitHub; the table above is a local run
  of the same commands.
- `reset_telemetry` targets `DATABASE_URL`. It prints the database name and requires
  `--yes`, but will clear whatever database that variable names.
- `generate_scenarios` assumes the default thresholds and seeded documents. Running the
  detector with non-default thresholds changes the expected results.
- The recorded demo is the one v0.1 item that cannot be produced from the repository.
